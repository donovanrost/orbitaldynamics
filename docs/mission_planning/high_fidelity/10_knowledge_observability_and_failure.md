# Knowledge, Observability, and Failure

## Domain Ontology

The mature planner needs a consistent vocabulary across artifacts, models, docs,
and APIs.

Core terms:

- spacecraft
- fleet
- asset
- subsystem
- component
- model
- activity
- timeline
- plan
- branch
- objective
- constraint
- score term
- risk
- contact
- command
- resource
- state estimate
- evidence
- authority
- policy
- readiness
- provenance

The ontology should define canonical meanings, IDs, relationships, and artifact
field names. This prevents the roadmap from becoming a collection of
similar-but-different maps.

## Planning Knowledge Graph

As objectives, activities, models, constraints, policies, evidence, and
artifacts grow, the planner needs relationship-level traceability.

Relationship examples:

- objective depends on activity
- activity depends on subsystem state
- activity consumes resource
- activity produces data product
- constraint comes from ICD rule
- policy comes from ops rule
- model implements capability
- artifact generated by model version
- warning traces to stale input
- approval requirement traces to authority rule

This does not require a graph database at first. It requires artifacts to carry
consistent relationship IDs that can later be indexed.

## Planner Observability

Long-running planning systems need operational telemetry about the planner
itself.

Planner observability fields:

- planning runtime
- propagation runtime
- branch count
- scenario count
- candidate count
- selected activity count
- rejected candidate count by reason
- search/solver effort
- memory or payload size
- artifact size
- model adapter runtime
- fallback paths used
- timeout events
- partial-result status
- validation/runtime warnings

These metrics should be available in artifacts and logs so operators and
engineers can understand planning cost, scale limits, and failure modes.

## Service-Level Reliability

If OrbitalDynamics runs as a durable planning service, the service itself needs
reliability features.

Feature areas:

- health checks
- degraded service mode
- queue depth
- retry policy
- rate limits
- dependency status
- timeout policy
- partial-result policy
- disaster recovery expectations
- service-level objectives
- operator-visible outage status

Service reliability should be separate from mission model fidelity. A valid
model can still be unavailable, slow, or degraded as a service.

## Mission Performance Analytics

After plans execute, the planning system should help measure mission
performance.

Analytics areas:

- objective fulfillment rate
- contact success rate
- data latency trends
- battery margin trends
- storage margin trends
- station utilization
- spacecraft utilization
- payload utilization
- maneuver success trends
- planning churn
- approval bottlenecks
- operator workload trends
- model prediction error trends
- campaign delivery confidence

These analytics can feed future planning priorities, model calibration, and
operational process improvements.

## Uncertainty and Margins

Operational plans should include uncertainty, not only nominal values.

Feature areas:

- orbit/state uncertainty
- maneuver execution uncertainty
- activity duration uncertainty
- power generation uncertainty
- power load uncertainty
- data volume uncertainty
- downlink rate uncertainty
- weather/provider uncertainty
- station schedule uncertainty
- model parameter uncertainty
- reserve policy
- safety buffers

Artifacts should expose nominal, margin, and risk views.

## Telemetry Calibration Loop

The mature planner should compare predictions against realized operations.

Examples:

- predicted battery after activity vs telemetry
- predicted storage fill vs recorder telemetry
- predicted downlink throughput vs realized throughput
- predicted maneuver result vs accepted OD state
- predicted activity duration vs actual duration
- predicted contact success vs contact outcome

Outputs should include:

- residuals
- calibration recommendations
- model drift warnings
- confidence updates
- model version review triggers

This is how the planner becomes more useful over mission lifetime without
pretending to learn hidden truths automatically.

## Failure and Degraded Operations

Degraded operations should be a first-class planning mode.

Representative cases:

- failed payload
- low battery
- antenna unavailable
- recorder near full
- propulsion inhibited
- ADCS degraded
- thermal constraint active
- ground station unavailable
- safe mode
- recovery planning
- missed contact
- failed maneuver
- delayed OD update

The planner should generate safe alternatives, identify blocked actions, and
separate recovery recommendations from normal planning recommendations.

## Authority and Safety Boundaries

The planner must distinguish:

- what is physically feasible
- what is operationally allowed
- what requires operator review
- what requires mission authority
- what is blocked by policy
- what an external system may execute

Authority boundaries should cover:

- commands
- maneuvers
- payload activation
- degraded-mode activity
- station reservations
- contact schedule changes
- onboard software changes
- recovery operations

OrbitalDynamics should classify and explain. Cadence and mission operations
should own approval workflow and execution.
